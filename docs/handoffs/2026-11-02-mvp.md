## Decisions since the last handoff

The full reasoning and the rejected options are in `docs/architecture/decisions.md`:
- "Booking resilience browser proof — 2026-10-28"
- "Keyboard focus reveals the whole calendar date — 2026-10-29"
- "Appointment retention browser proof — 2026-10-31"
- "Signed-out Home opens login — 2026-10-31"
- "Email and password sign-in for the MVP — 2026-11-01"

The short version:

- **Until the MVP ends, people sign up and sign in with email and password, and the email is trusted without proof** (#28). Email delivery is not configured, and the email-link flow only works locally through the development inbox, so it cannot create real test accounts. The address is marked verified so booking contact rules, invitations, admin promotion and review notifications work. The user accepted the risk that whoever signs up first with an address owns it in Visit. `PasswordCredential.unprovenEmail` marks those accounts for re-verification. Details, limits and local test-account steps are in `docs/architecture/password-authentication.md`.
- **Proving the address beats the unproven password.** The owner's email-link sign-in deletes a password registered with that address without proof and ends its sessions. Removing the email removes the password.
- **Email and password come first on the login screen; phone sign-in shows only when SMS is configured.** In development SMS is off, so phone is hidden. The browser suite configures SMS, so the phone journeys keep their coverage.
- **Signed-out Home redirects to `/auth/login`** (#27). A failed or unfinished session lookup still shows `SessionLoading` with retry, so a network error never sends a signed-in person to login.
- **Cutoff refusals have their own API codes,** `409 RESCHEDULE_CUTOFF` and `409 CANCELLATION_CUTOFF`, and the app has copy that says why. A missing booking policy stays `CONFLICT`; the security review caught a version that merged the two.
- **Customer-facing refusals and load failures always show the app's localized copy, never the server's message.** `bookingLoadRefusalKey` maps a 404 to "not accepting bookings", because a business that doesn't exist and one that is unpublished answer alike.
- **Slice (b) proves unpublish-during-review in the browser instead of hold expiry.** Hold expiry is cited from `apps/api/test/publication.test.ts`. Calendar export and business switching are cited from the seeded suites.
- **The deflake changed the test, not the app** (#24). A user would have to press Escape within one render of the sheet opening.

## Lessons (these will recur if forgotten)

- **A busy `ActionButton` keeps its accessible name on the spinner.** `getByRole('button', { name })` matches while it is still busy, so wait for the visible label text (`settled()` in `appointment-retention-smoke.ts`) before a screenshot or an assertion.
- **React Native Web's `Modal` becomes active one render after its content appears.** Wait for `role=dialog` before pressing Escape. `home-navigation-smoke.ts:40` still checks focus in the same tick after Escape. It is the same race class, though it hasn't been seen failing.
- **The per-phone OTP cooldown refuses a second sign-in for the same phone within minutes.** Hand a browser session between suites with Playwright `storageState` (`resume()` in `scripts/pilot-customers.ts`) rather than signing in again.
- **Redis reservation entries expire with the hold, even for a confirmed booking.** Confirmed capacity lives in PostgreSQL. "Nothing held in Redis" means no hold record and no capacity member without a confirmed booking. It does not mean "the key set is unchanged", and a check written that way fails at random.
- **A background command's "exit code 0" is the wrapper's.** Read the `suite exit N` line and the PASS count. One run reported 0 while the suite had failed at 37 PASS.
- **Linear auto-closed VIS-14 on #20 but not on #25.** Keep checking the issue state after every partial-slice merge.
- **Auth changes get `bf-security-reviewer` before merge.** On #28 it found three real issues (an unproven password surviving the owner's email link, lock-out by trying someone's address, a removed email's password coming back). All three are now tested.

## Running locally (worktrees)

- **A new worktree has no `.env` and no generated Prisma client.** Run `DATABASE_URL=postgresql://x@localhost/x npm run db:generate --workspace @visit/api` first.
- **The main checkout's `.env` cannot be `source`d by the shell,** because of the `<...>` in `EMAIL_FROM`. Load it with Node instead: `npx tsx watch --env-file=/Users/a/projects/Visit/.env src/server.ts`.
- **`SMS_DELIVERY_MODE` defaults to `disabled`,** so phone verification fails and the login screen hides phone. Set `SMS_DELIVERY_MODE=local-inbox` only when you need phone locally.
- **Ports:** the dev app uses API 3000 and web 8081 (`EXPO_PUBLIC_API_URL=http://localhost:3000`). The browser suite uses 3001 and 8082, and `VISIT_TEST_WEB_PORT=8083` avoids a clash with a running dev app.
- **Docker containers:** `visit-postgres-1` (5432) and `visit-redis-1` (6380) belong to the main checkout's compose. `main` has 32 migrations; #28 added `20261101120000_password_credentials`. Run `npm run db:deploy --workspace @visit/api` against the dev database if it predates that.
- **Test accounts:** follow "Creating test accounts locally" in `password-authentication.md`. The administrator is promoted with `apps/api/scripts/promote-admin.ts`, which signs them out.
- **A `.claude/launch.json` with `api` and `web` entries** was used in the browser pane. It is not committed, because it holds a machine-specific path.
- **The API test suite in a worktree needs explicit env.** That keeps it off the dev database and away from `.env`:
  ```
  DATABASE_URL='postgresql://visit:visit_local_only@localhost:5432/visit_test?schema=public' REDIS_URL='redis://localhost:6380/1' SESSION_SECRET=$(openssl rand -base64 33) SMS_DELIVERY_MODE=local-inbox npm test --workspace @visit/api
  ```
  The `visit_local_only` password is in the committed compose file and `.env.example`; it is not a secret.

## Debt and its consequences

**MVP sign-in (#28), all to finish before the MVP ends:**
- **No password reset or change.** A user who forgets their password has no way back in, and an administrator cannot help without the database. Both need real email delivery.
- **Accounts whose `unprovenEmail` still equals `Identity.email` are not re-verified.** Until they are, an address taken by someone else stays theirs, and Visit's mail about it goes to whoever registered it.
- **Account shows the unproven email as verified and does not list the password as a sign-in method.** The user cannot see or remove the password from Account.
- **Passwords are checked for length only (8–128).** Common passwords are accepted.
- **Sign-up answers `409 EMAIL_TAKEN`,** which reveals that an address is registered. Accepted for the MVP.

**Booking:**
- **After an unpublish during review, the bottom alert says "choose an available time again",** but nothing is bookable. The customer is pointed at a dead end.
- **`saveName` in `BookingContactFlow.hook.ts` still shows the server's message.** That is English on a Hebrew screen, the class of bug #25 fixed elsewhere.
- **A provider rescheduling inside the window is refused by the customer cutoff.** This predates slice (b) and needs a product decision.
- **One customer can hold overlapping bookings from two tabs** while places remain (#22, finding C3). This is an open product decision recorded in the decision log, and belongs with VIS-17.

**Tooling:**
